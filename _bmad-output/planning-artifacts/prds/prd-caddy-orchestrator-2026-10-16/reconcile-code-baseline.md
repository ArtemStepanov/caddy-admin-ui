# PRD source-code baseline reconciliation

Date: 2026-10-16. Method: source and documentation inspection; tests, Compose, and browser flows were not run in this extraction. Implementation presence below does not establish operational reliability.

## Implemented capabilities

- **Scoped ownership:** one Caddy instance and one selected HTTP server per SQLite database. Runtime writes its `apps/http/servers/<name>/routes`; the older `BuildCaddyConfig` produces test fixtures, not runtime `/load` requests. Normal synchronization does not regenerate other apps, TLS, logging, or listeners. Sources: `CLAUDE.md`, `README.md`, `internal/api/managed.go` (`syncRoutesLocked`), `internal/config/builder.go` (`BuildCaddyRoutes`, `BuildCaddyConfig`). This corrects the earlier assistant assumption that synchronization replaces the entire Caddy configuration.
- **Route operations:** reverse proxy, file server, and redirect CRUD; enable/disable, host matching (including comma-separated hosts and wildcard), path matching, path-prefix stripping, and response headers. Proxy options include multiple upstream dial strings, request headers, and a balancing policy. File-server options include root, browse, index, hide, and precompressed files. Redirects support destination and status code. The dashboard provides domain/path search, type filtering, forms, and raw JSON inspection for read-only routes. Sources: `internal/storage/models.go`, `internal/config/builder.go`, `web/src/pages/RouteForm.tsx`, `web/src/pages/Dashboard.tsx`.
- **Mutation behavior:** before setup, changes are saved as local drafts with warnings. After setup, a candidate is applied to Caddy before local persistence. Remote write failure prevents candidate persistence; local persistence failure after a remote write triggers a rollback attempt. Manual synchronization is available separately. Sources: `internal/api/handlers.go` (CRUD), `internal/api/managed.go` (`mutateRoutes`, `syncRoutesLocked`).
- **Setup:** connection test, server discovery, route preview, content-derived preview token, refetch on confirmation, explicit ownership, and an initial snapshot. Changed previews are rejected. Local UI-owned routes absent from live Caddy are retained in the local list and are not applied during confirmation. The Admin API URL is runtime configurable; changing it clears ownership/setup/ETag state. A completely empty Caddy can receive an initial HTTP server listening on `:80` and `:443`; a nonempty configuration with no HTTP servers requires a server to be created elsewhere. Sources: `internal/api/managed.go` (`buildSetupPreview`, `ConfirmSetup`), `internal/api/handlers.go` (`UpdateConfig`), `web/src/pages/Settings.tsx`.
- **Configuration protection:** a process-local mutex serializes mutations; the remote ETag is compared with the stored ETag and writes use `If-Match`. Drift produces a conflict with guidance to review/setup again. External routes without a valid owned `caddy-admin-ui-route-<uuid>` marker remain read-only even when the handler is familiar; their original raw JSON is stored and included in the new route array. The API rejects edit/delete/toggle for read-only routes. Sources: `internal/api/managed.go`, `internal/config/parser.go` (`ParseCaddyRoutes`), `internal/config/builder.go` (`BuildCaddyRoutes`), `internal/api/handlers.go`.
- **Snapshots:** ordinary route-array writes first save live raw routes, server name, ETag, reason, and timestamp; initial setup also records a baseline. Restore validates current ownership/server/ETag, snapshots the current array before restoring, applies the old routes, and updates SQLite. Export contains only a JSON route array. Fixed retention already exists: 100 snapshots are retained and the list API returns 50. Sources: `internal/api/managed.go`, `internal/storage/sqlite.go` (`CreateSnapshot`, `ListSnapshots`). Therefore, “no retention exists” is incorrect; configurable retention and a complete backup workflow are missing.
- **UI authentication:** one environment-defined HTTP Basic Auth account protects UI/API/readiness. There are no application users, sessions, login/logout UI, or roles. Both credential variables must be set together; without them loopback is allowed, while a non-loopback listener is rejected unless explicitly overridden. Mutating requests require a custom CSRF header; cross-origin Origin hosts are rejected; request bodies are limited to 1 MiB. CSP and other security headers exist. Source: `cmd/server/main.go`.
- **Deployment:** the main Compose stack includes UI and Caddy with persistent volumes. UI, HTTP, and HTTPS are published only on loopback; the Caddy Admin API is not published on the host. Compose explicitly enables unauthenticated access for this loopback scenario. `docker-compose.prod.yml` runs only the UI against existing Caddy, requires credentials/URL, and defaults to loopback host binding. The preview stack is isolated and loopback-bound. Sources: `docker-compose.yml`, `docker-compose.prod.yml`, `compose.preview.yml`, `README.md`.

## Missing capabilities and decisions required

1. **TLS/certificate management is absent:** no certificate inventory/expiry, issuer/DNS provider/ACME account options, DNS challenge credentials, public/internal/off TLS selection, local CA trust assistance, or upstream TLS transport. Global configuration contains only the Caddy URL, compression, and internal setup state. Normal writes intentionally leave TLS/server configuration untouched. A new “NPM for Caddy” scope must explicitly define safe TLS ownership rather than promise it on top of the route-only architecture. Sources: `internal/storage/models.go`, `internal/api/routes.go`, `internal/config/builder.go`, `README.md` current limitations, `ROADMAP.md`.
2. **Service access and diagnostics:** no route-level Basic Auth/access lists, certificate status, upstream health/health checks, access-log viewer, route reordering UI/API, or transport timeout/TLS options. `README.md`/`ROADMAP.md` state these omissions, consistent with the route types and API. Multiple upstreams and balancing do not constitute health checks. Admin API reachability does not establish that a published domain works.
3. **Publication/application status:** `/api/status` reports Admin API online/offline, latency, in-memory last synchronization result, setup, and route count. There is no persisted per-route applied/pending/failed state or DNS/TLS/upstream data-plane verification. Last synchronization timestamps/errors disappear after UI restart. Saving compression in Settings only persists SQLite configuration; the next sync/CRUD applies it. `UpdateConfig` does not immediately write to Caddy. Sources: `internal/api/handlers.go`, `internal/api/managed.go`, `web/src/components/StatusBadge.tsx`, `web/src/pages/Settings.tsx`.
4. **Backup/upgrade:** snapshots cover one route array; they do not back up the whole SQLite database, Caddy configuration, certificates, keys, or CA state. A user-facing database backup/restore command, compatibility policy, and tested upgrade/rollback guide are absent from the inspected material and remain on the roadmap. Snapshot export must not be presented as complete disaster recovery.
5. **Onboarding:** technical setup currently lives in Settings, without first-admin creation or guided domain/network/HTTPS troubleshooting. Main Compose includes `app.localhost`, `files.localhost`, and `readonly.localhost` examples rather than a clean homelab installation wizard. File-server roots refer to the Caddy container filesystem; mount/permission guidance is needed. README identifies the application as alpha.
6. **Route cloning is absent:** API routes expose CRUD/details/toggle/sync/setup/snapshots; dashboard actions are edit/toggle/delete or view JSON. The internal `cloneRoutes` helper copies mutation candidates and is not a user-facing clone feature. Sources: `internal/api/routes.go`, `internal/api/managed.go`, `web/src/pages/Dashboard.tsx`.

## Unverified risks: do not present these as proven runtime failures

- **Caddy restart persistence is a priority verification target:** Compose runs `caddy run --config /etc/caddy/Caddyfile --adapter caddyfile` without `--resume`. Mounting `/config` does not itself prove that API changes will be loaded after restart. The explicit startup input is a static Caddyfile; the UI does not automatically synchronize on startup. Verify create route → restart Caddy → request domain → restart UI → edit route. Sources: `docker-compose.yml`, `compose.preview.yml`, `cmd/server/main.go`. This is particularly important before a dependable first release. The inspected README has no restart-persistence/resume procedure or explanation of restart configuration authority. `ROADMAP.md` lists backup/upgrade/rollback guidance as future work. `restart: unless-stopped` describes container restart policy, not API-configuration persistence.
- **Ambiguous remote outcomes:** if PATCH succeeds but the subsequent ETag GET fails, synchronization returns `routes applied but new ETag could not be read` before local route persistence. Guidance, snapshots, and re-setup exist, but durable operation state/reconciliation does not. Best-effort rollback does not provide an atomic SQLite+Caddy transaction either. Source: `internal/api/managed.go` (`syncRoutesLocked`, `mutateRoutes`). Product requirements should demand honest unknown/applied-with-local-error states, rather than promise “nothing changes on every error.”
- **Setup snapshot exception:** empty-instance bootstrap writes `apps` before the first snapshot; a missing routes array is initialized by a scoped server PATCH. Thus, “every Caddy write has a preceding snapshot” is too strong. Ordinary mutations and restores have pre-write snapshots; bootstrap needs a separate acceptance case. Source: `internal/api/managed.go` (`ConfirmSetup`).
- **Upstream scheme and validation:** the builder passes upstream strings directly into Caddy `dial` and does not create a TLS transport. Backend validation checks a nonempty upstream list, not the complete upstream/domain format, file root, or allowed redirect codes. Accepting a string in the UI does not establish HTTPS upstream support. Real HTTP, HTTPS, IPv6, and Docker-service upstream scenarios need verification and understandable validation errors. Sources: `internal/config/builder.go` (`ValidateRoutesForBuild`, `buildReverseProxyHandler`), `web/src/pages/RouteForm.tsx`.
- **Fresh/existing-install HTTPS:** a host route and open ports do not establish certificate issuance and service reachability in this extraction. Existing servers may have arbitrary HTTP/TLS settings outside current UI ownership. Real public-domain and internal-CA flows were not exercised.
- **Coverage boundary:** `internal/caddy/integration_test.go` contains a scoped PATCH/ETag preservation test. This is not full-product browser setup→CRUD→HTTPS→restart→restore validation. No tests were run in this extraction.

Checked tasks are historical implementation evidence, not the authority for current endpoints/semantics. In particular, local-only drafts are now retained rather than deleted, and ETags already block drift.
- `specs/002-code-cleanup/spec.md` is Archived, Status Implemented, with checked tasks. It covers mode-safe form cleanup and safe import validation, not the new product PRD.
- `ROADMAP.md` is useful prior intent and explicitly excludes arbitrary external JSON editing, multi-tenant RBAC, active-active operation, and public Admin API exposure. The user's new goal may change priorities; roadmap entries are not automatically accepted requirements for the new PRD.

## Proposed PRD directions above this baseline

- First prove the complete happy path and survival after UI/Caddy/container recreation. Preserve scoped ownership, raw external route preservation, ETags, and snapshots as regression requirements.
- Specify public-domain, LAN-only, and HTTPS-upstream scenarios separately, including prerequisites, DNS/network/CA trust, and an honest distinction between configuration acceptance and verified service reachability.
- Design a modern UX around a clear service inventory and troubleshooting. Do not equate enabled with healthy, or Admin API online with HTTPS ready.
- Specify new TLS/access/operability capabilities and any ownership expansion separately. Do not introduce already implemented safety mechanisms as entirely new work.
