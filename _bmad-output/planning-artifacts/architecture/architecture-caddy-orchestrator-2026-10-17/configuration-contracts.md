# Configuration safety and lifecycle contracts

Approved through [P01–P13](../../sprint-change-proposal-2026-10-17.md). These are future implementation contracts, not a description of current source. The spine's stable AD identifiers govern the boundaries; this companion fixes shared protocols and data shapes. No product runtime validation is claimed.

## P02 — Use remotely guarded root writes and reviewed reconciliation (B01)

“Apply and restore submit one complete JSON candidate using `POST /config/`, `Content-Type: application/json`, and the exact root ETag from the reviewed baseline as `If-Match`. The root conditional mutation is the remote concurrency guard. A preceding GET is for review/recovery, not protection by itself. Remote 412 becomes application HTTP 409 conflict, preserving the candidate; there is no fallback to `/load` or unconditional retry.”

Bind a review token to target/adoption generation, draft revision, baseline ETag, candidate identity and preservation/dependency manifest. Any change invalidates that review. Restore binds the same fields to the selected recovery point and live baseline captured during comparison; target mismatch blocks before submission. Require real Caddy 2.9.1 tests for root replacement, empty/null root bootstrap and a competing write inserted between final read and submission. Block unsupported targets rather than weaken the guard.

Rebase compares original baseline B, latest live L and draft candidate C. Nonoverlapping, provably mapped edits may form a proposed merged draft; overlapping edits, deletion-versus-edit and ambiguous array/source identities require explicit resolution. Preserve original inputs, show conflicts and require a new diff review. Updating only the ETag is forbidden. Discard needs a fresh safe source association under P03; if live cannot be represented, retain the draft and show compatibility blocking rather than fabricate Caddyfile.

External writers can still replace configuration *after* a successful guarded write; detect subsequent drift and mark observations stale. This is not an exclusive-writer guarantee or a transaction spanning Caddy and SQLite.

## P03 — Make source acquisition and preservation explicit (B02)

“Adoption stores a protected exact runtime baseline and an explicit source bundle, provenance and dependency manifest. Source is operator-supplied or obtained through a configured read-only source path; manager-only network access does not imply access to Caddy's filesystem. Missing source is a source-required state. JSON-only conversion is allowed only for a tested converter whose output passes the same equivalence/preservation checks; it never recreates original comments/imports.”

Use this concrete composition model:

1. B is the live root JSON, E its root ETag, S the exact supplied source bundle, and G0 the target-adapted result for S. Store all identities and source/build/dependency provenance. Adoption preview binds them; refetch live and reject a changed preview before local confirmation. Adoption performs no configuration write, including on empty Caddy.
2. Produce a path ownership manifest: generated/mapped subtrees versus preserved raw subtrees. It includes nested routes, server/listener settings, other servers, root `logging`/`storage`, and `apps.pki`; these are not all applications. Unknown/overlapping ownership or unexplained B/G0 differences block editing/publication of the affected configuration.
3. For candidate source S1, adapt to G1 and compute intended generated changes G0→G1. Apply only mapped changes onto B. Copy preserved subtrees without reconstruction; preserve array order. A change to a parent containing preserved descendants, route regrouping or a server-name remap needs a proven mapping and preservation test; otherwise block with the exact collision. Never use a generic recursive merge or replace the entire HTTP app by default.
4. Diff exposes both source edits and the resulting root-JSON delta, including preserved scope. The review identifies every changed runtime path. Source and semantic equivalence use versioned comparison rules under P04, not text equality of JSON.
5. External imports require a bundle manifest with ordered resolved file paths, exact contents/digests, expansion context and ownership. Adapter-visible dependencies must be reproduced on target and frozen for the compilation/review window, or supplied as a deterministic compiled bundle with source mapping. If dependency freshness/immutability cannot be established, block publication. No remote filesystem-write mechanism is implied. Keep originals separately; do not claim expansion preserves source formatting.
6. Source syntax errors, missing dependencies, unrepresentable runtime JSON and unknown module handlers retain protected source/runtime copies and actionable compatibility states. They do not silently narrow the requested all-settings goal. Changing targets detaches and retains prior drafts/history; it never binds them to the new target or silently clears unsaved work.

## P04 — Persist attempts and reconcile content after interruption (B03)

“Before submission, one local transaction commits the pre-write recovery point and a durable apply/restore attempt: attempt ID, operation, target/adoption generation and immutable connection descriptor, draft revision, reviewed ETag, protected baseline and exact candidate, comparison version and status `prepared`. No remote mutation occurs if this transaction fails. Commit `submission_possible` before sending; startup treats every unfinished attempt as reconciliation-required.”

Successful response alone does not finalize local state. Read back root state, compare content, and atomically record the observed applied revision plus finalized attempt. Response loss, readback failure, crash or failed local finalization keeps the attempt unresolved and blocks further mutations. If even recording uncertainty fails, fail closed in memory; the precommitted unfinished attempt reinstates the lock on restart. Never retry the mutation automatically.

Content comparison: parse JSON with exact number handling; compare objects independently of key order, arrays in order, numbers by exact numeric value, and missing separately from null. Do not remove unknown fields/defaults or reorder arrays. Version the algorithm and golden fixtures. If Caddy normalization prevents a proven comparison, outcome remains unresolved. Do not compare opaque Caddy ETags to manager hashes. Protected comparison material includes hydrated historical secret versions; equality digests exposed locally use a keyed digest rather than a secret oracle.

| Reconciliation observation | Result |
| --- | --- |
| Live equals candidate | Record candidate currently present, finalize local baseline, enqueue verification; lost response does not prove historical causation. |
| Live equals baseline and differs from candidate | Record baseline currently present, preserve unapplied candidate for renewed review; no assertion that it was never temporarily active. |
| Live differs from both | Conflict; retain attempt/draft and require explicit resolution and renewed review. |
| Live unavailable / comparison or secret material unavailable | Remain reconciliation-required; explain missing evidence. |

If candidate equals baseline, treat as a no-op and report current equality without inferring a unique remote outcome. Authoritative rejection/precondition responses are distinct from arbitrary proxy/server errors; ambiguous failures still require readback.

## P05 — Protect every source representation and historical secret version (B04)

“Initialize the encryption key and vault before importing any baseline. Protect exact source bundles, runtime originals, legacy archives, draft buffers and recovery payloads using authenticated encrypted envelopes; extracted known secret fields use typed references to immutable secret versions. Unknown opaque content is encrypted and withheld from ordinary API/editor output until its display/redaction mapping is proven. No secret-bearing source text is stored as plaintext merely because JSON was sanitized.”

Keep immutable secret versions while referenced by a retained draft, attempt or recovery point. Rotation creates a new version; deleting a current credential cannot destroy retained recovery material. Missing key/version blocks adapt/apply/restore with an explicit error. Garbage collection follows reference retention, including unresolved attempts.

Use API actions `keep(reference, version)`, `replace(value)` and `remove`; absence and display masks never mean replacement. The editor shows stable typed reference tokens, not masked literal credentials; validate tokens against server-side ownership/version metadata. Materialize secrets in memory for remote adaptation/submission only. Sanitize remote error text, warnings, logs, diffs and exports. Unknown secret-bearing blocks require safe opaque handling rather than a false universal redaction claim. Ordinary exports are sanitized and labelled incomplete for standalone secret recovery; full protected backup includes key material by the documented procedure.

## P06 — Version shared drafts and asynchronous observations (B07)

“Every persisted draft mutation includes the expected draft revision. SQLite atomically increments it only on a matching revision; stale writes return HTTP 409 with latest revision and preserve the client's unsaved buffer. SSE carries target generation/revision and monotonic event identity. Reconnect fetches authoritative state and offers explicit reconciliation for unsaved input; incoming events never overwrite it.”

Add target ID/adoption generation, draft revision, applied configuration revision, attempt ID, probe job ID, expectation version and source/dependency manifest identity where relevant. Jobs/results bind to the exact applied revision and target. Late results remain historical, visibly stale, and cannot mark the current revision verified. Restore creates a new applied revision even when content matches older history. Target changes cancel/detach jobs and invalidate review tokens.

## P07 — Define complete form and brownfield regression coverage (B06)

“Maintain a versioned supported-build/settings inventory mapping every setting to form representation, Caddyfile/CST representation, runtime path, validation, secret classification and round-trip test. A required setting without a form is an implementation gap, not accepted editor-only completion. Expose compatibility gaps and block destructive conversion. Preserve Caddyfile as the chosen peer editor.”

New story: **Edit existing global and server settings through forms and Caddyfile.** Acceptance: existing global/server values appear in forms; form edits and text edits produce the same candidate; shared snippets and affected routes are shown in review; unknown constructs survive unchanged; incompatibility blocks with retained input; no supported inventory setting is marked complete without a form/round-trip mapping. Build-specific forms may use declarative schemas, with custom controls where schemas cannot express directive semantics. Pin the reference build/module inventory before completing this story; arbitrary plugins are never advertised without coverage.

Explicit retained-feature matrix: multiple upstreams and load balancing; host/path matchers and prefix stripping; request/proxy/response headers; encoding/compression and when it applies; redirects; file roots/browse/index/hide/precompression; ordering, disabled/local-only routes, raw external data and global connection settings. Each maps to migration, editing, apply and regression checks or an explicit blocking incompatibility. No feature silently disappears behind generic “CRUD”.

## P08 — Report bounded verification and correct Caddy API claims (B08, B09)

“`GET /config/` supplies live JSON and its ETag. Build/version/module inventory needs separately supplied, provenance-labelled build evidence or a supported capability mechanism; absence is unknown. `POST /adapt` with `text/caddyfile` returns the `result` JSON and optional warnings, or an error; decode the wrapper. It proves adaptation only. Remove the `validate=true` semantic guarantee. Provisioning may still fail on guarded application.”

Known missing-module adaptation errors block. Successful adaptation is narrower evidence, not an installed-module inventory. DNS-01 supported builds/providers require pinned build/module manifests and real compatibility cases including missing-plugin and provisioning failure. Unknown capability is shown explicitly; unsupported advertised scenarios cannot be declared complete. Use `/pki/ca/local/certificates` for chain retrieval, validate/select the root for a root-only download, and explain that the PKI request can provision the default CA. It is an explicit requested operation, not a side-effect-free generic connection probe. These contracts follow [pinned adapter code](https://github.com/caddyserver/caddy/blob/v2.9.1/caddyconfig/load.go#L120-L193) and [PKI API documentation](https://caddyserver.com/docs/api#get-pkicaidcertificates).

**Verification contract:** “Store observed DNS/TCP/TLS/HTTP facts separately from diagnostic hypotheses. A 502 is an unexpected HTTP response unless additional evidence identifies the cause; a file response 403 does not prove a permission problem. Direct upstream probes are separate observations with manager-network limitations. Published-service checks use the published URL, not Docker upstream names.”

Per-route expectations name scheme, hostname/SNI, port, path, allowed status codes, redirect Location policy and trust roots. Protected services may expect 401/403. Redirect probes do not follow the first hop. File probes use a known resource. Proposed initial timing defaults: 10-second per-check deadline, no automatic configuration resubmission, manual retry plus a bounded two-retry schedule at 5/15 seconds for transient observations; evidence becomes stale after five minutes or immediately on revision change. These are reviewable defaults, not supplied product performance targets. Certificate near-expiry warnings are distinct from certificate validation failure.

Browser Fetch failure may reflect CORS/CSP/mixed content/client trust; classify unavailable/unknown unless evidence establishes more. Opaque responses do not establish expected status/headers. Preserve a manual open-and-check path. Design CSP narrowly for explicitly selected probe origins; do not add wildcard outbound access. Client and manager results stay separate; final success names only the type, expectations, revision, time and vantage actually verified. Required unavailable checks leave the outcome applied/unverified or partially verified. [Fetch response model](https://fetch.spec.whatwg.org/#concept-filtered-response-opaque) supports these browser limits.

## P09 — Specify a functional upgrade rather than archive-only migration (B10)

“Use a versioned, transactional, restart-safe migration preserving usable local data without contacting or writing Caddy during database migration. Preserve a protected prior-schema backup and record migration version/checksum. If conversion fails, roll back and retain a usable recovery path; never mark migration complete from table existence.”

| Legacy data | Target treatment |
| --- | --- |
| Route ID/order/domain/path/handler/config/headers/prefix stripping | Mapped records with old-to-new identity and exact protected payload until source adoption validates canonical projection. Preserve all handler config fields. |
| Enabled and disabled/local-only routes | Preserve enabled state and locally stored intent separately from observed live baseline; do not silently publish missing/disabled routes on upgrade. |
| Raw external route, support status and reason | Protected raw preservation with exact order and scoped provenance; promotion to editable requires verified mapping. |
| `global_config` URL/encoding/server/setup/ETag | Preserve settings and legacy ownership record; root ownership remains pending explicit adoption. A route ETag cannot become a root ETag. |
| Route-array snapshots | Retain original ID/time/server/reason/ETag and `legacy_route_array` scope; allow inspection/export and only scoped reviewed restore where compatible. Never relabel full-config history. |

Canonical source becomes active only through P03 association; migrated local intent remains accessible and is reconciled against that baseline. Build an actual prior-release DB fixture including disabled routes, custom settings, raw routes and snapshot history. Cover repeated startup, interrupted migration, failure rollback and preserved editing/restore access. Document downgrade via protected prior-version backup and compatible image; no unsupported in-place downgrade promise.

## P10 — Complete backup scope and remote operator procedure (C03)

“A recoverable deployment package includes a consistent SQLite backup, encryption key/key provenance, current applied configuration plus source/dependency bundle, external startup configuration/autosave (`/config` where applicable), certificate/CA assets (`/data` or configured storage equivalent), and deployment/build/import/environment assets required to reproduce the target. Record exact scope and acquisition time in a manifest.”

Use SQLite's consistent backup mechanism or an explicit stopped-manager procedure, not a naive copy of an active WAL database. Quiesce participating writers for a coordinated point-in-time package or label independently captured pieces and require reconciliation. External assets are acquired/restored by documented operator-side commands on the Caddy host. No manager Docker mutation or remote filesystem write privileges are added. Missing required assets make the package incomplete, not successful. Protect sensitive backup material and state key-loss consequences.

Clean-environment acceptance reconstructs both manager and external target, establishes source association, verifies current routes/settings/secrets/certificates and checks restart. UI recovery points exclude certificate private keys; sanitized configuration export alone is not this package.

## P11 — Finish identity and input boundaries (C04)

“Parsing never mutates source bytes. On explicit save, assign missing IDs and show the source delta; duplicate IDs block save with locations and a repair action. Keep existing IDs stable across formatting edits. Disable retains source and identity through versioned enabled metadata, omits the route from compilation, and restores the same definition on enable. Editor deletion and disabled-source edits have explicit candidate diffs.”

Proposed supported examples: `service.example.com`, `*.lab.example.com`, Unicode hostname with validated IDNA projection; path `/api/*` plus separate prefix-strip setting; `192.0.2.10:8080`, `whoami:80`, `[2001:db8::10]:8080`; HTTPS destination `https://backend.example.com:8443` with separate upstream TLS/SNI/trust settings. Ports are 1–65535; reject `://`, unbracketed IPv6 with ambiguous port, embedded credentials, and unsupported destination URL paths rather than silently dropping them. Multi-upstream order and transport constraints must survive form/editor round trips.

Redirect accepts the supported 301/302/307/308 codes and validated absolute or relative Location with documented placeholder handling; reject CR/LF. File roots resolve on Caddy's filesystem; accept an absolute root such as `/srv/www`, reject NUL, and flag unsupported expansion syntax without claiming the manager can inspect the directory. Pin full matcher/URI/IDNA/placeholder grammar in a validation companion with valid/invalid examples and actual target tests before story readiness. These examples define a proposed boundary, not a claim of complete Caddy syntax coverage.

## X1. Resolved composition and source envelope

A `SourceBundleV1` contains `entry_path`, an immutable versioned `enabled_nodes` map and `node_identity_map`, encrypted files keyed by normalized virtual POSIX path, ordered import resolution, secret-version references, explicit environment substitutions, source-map spans, comparison version and build manifest ID. The identity map binds node IDs to source spans/digests, including pre-annotation adopted nodes; first explicit save reuses those IDs in source comments. The enabled map is part of bundle identity/digest, review, attempt and recovery payloads. Apply compiles it; restore uses the historical map rather than retaining current flags. Missing legacy enabled metadata requires explicit compatible migration, never a default that reenables routes. No filesystem or environment values are inferred from the manager host. An operator-supplied bundle is an immutable captured input: later source-file changes are a different bundle and invalidate review. It need not track an external file after publication; root runtime drift is still guarded remotely.

Compilation uses an ephemeral flattened Caddyfile from that captured bundle. Resolve file imports against its virtual paths, expand snippets/arguments using pinned Caddy 2.9.1 token semantics, and preserve the originals unchanged in encrypted storage. Runtime request placeholders remain tokens; adapter-time environment substitutions are captured explicitly, with sensitive values referenced/encrypted. Detect import cycles, path traversal outside the bundle, unresolved globs and substitutions. Reject unsupported expansion semantics rather than silently using Caddy-host files. Story 1.4 delivers parity fixtures against the pinned adapter; until parity is proved for a construct, its publication is blocked with the offending source span. The expanded text is transient, never the editable source of truth. No mutable Caddy-host import is used during review/apply.

For initial adoption, require `compose(G0, preserved_manifest) == B` by versioned structural comparison. The initial implementation accepts identity mapping for matching JSON paths and exact generated array sequences; it does not guess semantic equivalence or server renames. A preserved field/route is an explicit raw path (and array position where relevant), with its baseline digest. Root fields and nested fields use the same mechanism. Review displays unexplained differences, which must be represented by explicit preservation entries before confirmation. Generated and preserved ownership cannot overlap. Native JSON-only content may remain preserved but cannot be advertised as form/Caddyfile editable without a codec.

At mutation, compute a structural delta from G0 to G1 and replay only proven mapped paths onto B. If an array contains any preserved member, treat that array as indivisible: a change to it is blocked until all members have a verified editable source representation; unchanged arrays are copied exactly. This deliberately prevents index guessing. Adding/removing a generated whole array is valid only when it contains no preserved member. Verify unchanged preserved paths/digests and ordered arrays in the final candidate before review. Server regrouping/renaming is blocked unless the manifest has an explicit one-to-one mapping verified by a fixture. A blocked compatibility case is a visible gap, not successful adoption/editing of that content. Full-config intent remains; no JSON editor is substituted for Caddyfile.

Rebase uses these same mapped paths: compare each C-vs-B change against L-vs-B, flag any ancestor/descendant overlap or change to an indivisible array as conflict. Nonoverlapping changes can prepare a new candidate only if fresh source association to L succeeds; otherwise require the updated source bundle. Keep B/C protected until the user accepts a newly reviewed candidate. No force apply exists.

## X2. Shared records and API envelopes

Identifiers are UUIDv4; timestamps UTC RFC3339. Object revision counters are monotonically increasing integers, separate from opaque Caddy ETags. Key identity fields are required, not optional UI metadata.

| Record | Required shared fields |
| --- | --- |
| TARGET | id, immutable_connection_descriptor_id, adoption_generation, write_mode (`legacy_routes` or `root`), build_manifest_id, compatibility_state |
| CONNECTION_DESCRIPTOR | id, immutable normalized endpoint URL, encrypted transport/auth reference versions, configured TLS identity binding, provenance, created_at |
| SOURCE_BUNDLE | id, target_id, generation, encrypted_payload including enabled_nodes/node_identity_map, manifest_digest, comparison_version, created_at |
| DRAFT | id, target_id, generation, revision, state, base_root_etag, base_bundle_id, candidate_bundle_id, encrypted_baseline_json, encrypted_candidate_json, preservation_manifest_id |
| APPLY_ATTEMPT | id, kind (`apply`/`restore`), target_id, generation, connection_descriptor_id, draft_revision, review_id, base_root_etag, baseline/candidate encrypted payload identities, prewrite_recovery_id, status, observed_applied_revision, comparison_version |
| RECOVERY_POINT | id, target_id, generation, connection_descriptor_id, scope (`full_config`/`legacy_route_array`), legacy_server, encrypted_source_bundle, encrypted_json, secret_version_refs, observed_etag, trigger, created_at |
| SECRET_VERSION | credential_id, version_id, encrypted_payload, nonce, key_id, immutable, created_at |
| APPLIED_REVISION | id, target_id, generation, attempt_id, bundle_id, encrypted_observed_json, observed_root_etag, observed_at |
| VERIFICATION_JOB/RESULT | job_id, target_id, generation, applied_revision_id, route_id, expectation_version, method, vantage, state, sanitized_evidence, observed_at, expires_at |
| SCHEMA_MIGRATION | version, source_schema_fingerprint, migration_checksum, completed_at |

SQLite foreign keys retain secret versions and attempt comparison material while referenced. An attempt acquires a durable target-and-draft lock in the same transaction as snapshot/intent preparation; preparing checks the reviewed draft revision again. All draft saves, source/secret-reference mutations, applies/restores and connection changes for that target are rejected while the attempt is prepared, submission-possible or unresolved. Read-only observation and reconciliation remain available. A finalized/rejected attempt releases the lock transactionally. Finalization updates only its captured draft revision via CAS and cannot erase a newer candidate; any unexpected revision mismatch stays reconciliation-required. One unresolved submission blocks another mutation on that target. Recovery retention is at most 100 history entries (oldest unpinned first); the active attempt's recovery is protected. When all 100 are pinned, reject new publication with capacity/reconciliation guidance rather than prune required evidence or exceed the bound. Attempts retain their own protected payload until resolved. Transactions enforce insertion/pruning together; secret garbage collection runs only after reference removal. Legacy route-snapshot retention remains explicitly scoped and does not manufacture full recovery points.

Connection descriptors are immutable and retained while referenced by attempts/history, including encrypted auth/transport versions. Reconciliation/readback always dereferences the attempt descriptor, never a mutable global URL. A target endpoint change after the lock releases creates a new target/descriptor identity and detaches old drafts; it cannot repoint old history/attempts. If original endpoint or transport identity is unavailable, old attempts remain unresolved with their own target locked. The manager has no universal API proof of Caddy physical instance identity: URL reuse/redeployment is not evidence of historical causation. Explicitly replacing a target requires new adoption and never finalizes the old attempt by probing the new target.

`GET /api/drafts/current` returns target/generation/revision/state and sanitized projections/reference tokens. A draft mutation requires `{target_id, generation, expected_revision, operation}`; mismatched generation/revision returns Problem Details HTTP 409 before persistence. `POST /api/changes/review` returns `review_id`, root ETag, candidate/bundle/manifest identities and redacted source/runtime diff. `POST /api/changes/apply` requires that review ID and expected revision. Review records are single-use and invalidated on any relevant change. `POST /api/recovery/{id}/review` prepares a restore candidate; `POST /api/recovery/{id}/apply` uses the same apply contract. Opaque record references are checked server-side; clients cannot submit trusted runtime JSON or secret references merely by naming IDs.

`GET /api/events` emits monotonic event ID plus target/generation/draft revision/applied revision and event kind. On a gap, reconnect or missing Last-Event-ID history, fetch current authoritative state. Private unsaved input buffers are allowed and never automatically overwritten; persisted projections remain in the shared Signals store. Events contain only sanitized projections. Verification retry requires current target/applied revision and never publishes.

Auth is enforced by listener configuration (not request remote-address inference). Paired credentials are always required together, including with insecure override. Non-loopback listening requires credentials unless explicitly overridden. Browser mutation origin/CSRF policy is retained across POST/PUT/PATCH/DELETE, including adoption, review, verification and restore; Basic Auth does not bypass it.

## X3. Build/settings coverage and validation boundary

Reference target is pinned Caddy 2.9.1. The first required DNS-01 provider adapter is Cloudflare; other providers require their own module/form/secret mappings and compatibility fixtures before advertisement. This selects an implementation reference provider, not a reduction of the four required TLS scenarios. Build evidence is an operator-supplied manifest from `caddy version`, `caddy list-modules --versions`, executable/image digest and module build lock. Story 1.5 provides the capture/validation procedure and records exact module dependency versions in its reproducible fixture; the manager does not execute remote shell commands. Unknown build evidence remains unknown and blocks a claim of provider compatibility. Adaptation can provide narrower evidence and actionable errors without manufacturing a module inventory. No target upgrade or dependency migration is introduced here.

Every directive/global option enabled by the reference build's Caddyfile adapter is inventoried, including server options, matchers, reusable snippets, TLS, logging and storage constructs. Form coverage has two concrete levels: dedicated task controls for retained route/TLS/common global options, and a structured directive form for remaining registered settings (directive selector, labelled ordered argument fields, nested block rows, matcher fields and explicit ordering). The latter is a form, not an editor-only escape hatch. Its codec shares CST nodes with the text editor. Unknown secret classification or grammar blocks display/edit until a descriptor exists. A build is not declared fully supported while any inventoried setting lacks a form descriptor, codec, validation, secret policy or preservation fixture. Story 2.5 generates and checks that exhaustive inventory against the exact module/build manifest; this is implementation work with explicit acceptance, not a future scope choice.

Descriptors have `build_id, setting_id, parent_context, arity, ordered_args, child_schema, secret_fields, caddyfile_codec, runtime_path_mapper, form_control, valid_cases, invalid_cases`. Option names newly introduced by a different build do not inherit a misleading supported label. Native JSON constructs with no Caddyfile representation are recorded as a compatibility limitation and preserved; adding a codec cannot claim original source reconstruction.

Hosts: accept DNS labels with IDNA projection, IPv4/IPv6 address literals and a single leftmost wildcard for domain matchers; show Unicode and ASCII forms. Reject empty labels, invalid IDNA, wildcards in other positions, host paths/userinfo and embedded CR/LF/NUL. Distinguish a route domain from an upstream URL. Paths: accept a leading slash path matcher, including a documented trailing `*`; exact `/api` and `/api/*` are distinct. Rich Caddy matchers use the structured matcher form and target adaptation; do not reinterpret them as prefix stripping. Strip-prefix is an independent setting. Unsupported matcher syntax is a field error, not silently normalized.

Upstreams: accept host:port, IPv4:port and bracketed IPv6:port with decimal port 1–65535; HTTPS uses `https://host:port` and separate SNI/trust fields. Multiple destinations preserve order and validate shared transport compatibility. Reject userinfo, query, fragment, embedded path and ambiguous unbracketed IPv6. DNS suggestions use addresses reachable by Caddy, not the manager/browser by assumption. Redirect Location accepts absolute http/https or relative URI references; supported request placeholders are represented as typed tokens and passed unchanged. Reject malformed placeholders, control characters and unsafe/unsupported schemes. File root accepts absolute Caddy-side paths and typed supported placeholders; reject NUL/CR/LF and unresolved adapter-time variables. Path validation never claims filesystem existence. Caddy-specific richer constructs remain form-accessible via validated descriptors rather than silently discarded.

Parse/serialize is byte-identical when unchanged. First save injects missing comment IDs with an explicit review delta; duplicate IDs require repair. Route identity refers to an explicit route node in a site, with separate site/node IDs where multiple routes share a site. Existing legacy IDs map to node UUIDs. Enabled metadata is persisted alongside source nodes; disabled source stays in the bundle but is omitted from transient compilation. No arbitrary user block is deleted as a means of disabling it. Golden fixtures cover multiple routes per site, nested handlers, comment movement, missing/duplicate IDs and disabled edits.

## X4. Migration and deployment implementation sequence

Story 1.1 detects the existing schema but performs no destructive migration; legacy mode can still run. Story 1.2 initializes encryption before importing protected material. Story 1.3 obtains a consistent protected backup, transactionally copies legacy data into versioned records, validates counts/IDs/order/settings/payload digests, commits schema version last and switches adapters only after commit. A crash either leaves the old committed schema or the completed new schema; restart checks the migration ledger. Existing raw plaintext legacy cells are not duplicated as permanent plaintext archives: encrypt their values before dropping active legacy rows in the migration transaction; checkpoint/vacuum maintenance and file-permission/runbook limitations for historical WAL/free pages are documented. The prior-version backup is encrypted and retained for downgrade recovery. No promise of secure erasure from arbitrary host storage is made.

Network access/adoption waits until after local migration and preserves its unresolved local intent separately. Import live configuration without automatically reenabling disabled/local-only records. Display their proposed reconciliation as draft changes. Legacy snapshots retain original scope and server; scoped restore composes that route array into the matching live root and uses the same reviewed root guard, without pretending the old snapshot captures current global config. A different target/server is incompatible.

Introduce ports/application/adapters per use case; keep the current implementation working until its replacement passes matching checks. `TARGET.write_mode` is enforced server-side so no legacy CRUD writer can address a root-adopted target. A process restart preserves that lock. Adoption does not grant simultaneous legacy/root writers. Source files and deployment settings remain operator-owned inputs; manager never provisions remote Docker or filesystems.

External Caddy must preserve runtime configuration at startup through `--resume`/documented equivalent and its persistent configuration/data storage. The API alone cannot prove remote mounts/startup flags: show operator-declared prerequisites and prove restart in the reference fixture. Keep the Admin API private on a reachable internal interface; manager default UI port is 3000. Complete backup includes externally acquired startup config/source/import/env/build assets and data in addition to consistent DB/key; operator executes remote-host acquisition/restoration. Any source/key omission marks the package incomplete. Recovery history is not full certificate or host backup.

## X5. Required fault and compatibility evidence

Before declaring a supported runtime scenario complete: pinned root write and empty/null bootstrap; remote 412 after a competing write; unsupported normalization left unresolved; stale source/import bundle; preserved nested route/server/PKI/logging/storage; conflicting rebase arrays; process kill before send/after send/after response/before local commit; DB-write failure; secret rotation and missing key/version; stale session save; late probe after restore; browser CORS/CSP/opaque/mixed-content states; expected protected-service status; missing DNS module and provisioning errors; legacy disabled route migration and failure rollback; external restart and clean backup restoration. Test plans map these to exact stories. These are planned gates, not completed tests.
